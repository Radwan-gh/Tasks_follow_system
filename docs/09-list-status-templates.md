# 9. قوالب حالات القوائم (List Status Templates)

المصدر: `apps/api/src/boards/board-templates.ts`،
`apps/api/src/boards/boards.service.ts` (دالة `create`)، والحقل `statusCategory`
في `apps/api/prisma/schema.prisma` و `packages/types/src/domain.ts`.

## الفكرة والدافع

في نموذج Kanban **حالة البطاقة هي القائمة التي تسكنها** (لا يوجد حقل "حالة"
منفصل). لتسريع بدء العمل، أُضيف **قالب جاهز** يُنشئ للوحة الجديدة خمس قوائم تمثّل
سير عمل قياسيًا للمهام، بدل أن يبنيها المستخدم يدويًا واحدة واحدة.

الحالات الخمس، بالترتيب:

| الاسم (بالعربية) | `statusCategory` |
|---|---|
| جديد | `NEW` |
| جاهز للتنفيذ | `READY` |
| قيد التنفيذ | `IN_PROGRESS` |
| تم التنفيذ | `DONE` |
| انتهى | `CLOSED` |

## حالتان نهائيتان لا واحدة: `DONE` و`CLOSED`

القالب ينتهي بحالتين متتاليتين، وهذا **مقصود**:

- **«تم التنفيذ» (`DONE`)** — أُنجِز العمل.
- **«انتهى» (`CLOSED`)** — سُلّمت المهمة وتم التأكّد منها.

الفرق بينهما ليس تجميليًا، لأن السؤالين المختلفين يُجابان بطريقتين مختلفتين:

| السؤال | الجواب |
|---|---|
| هل المهمة ما زالت **مفتوحة**؟ | لا، في كلتا الحالتين. تُستثنى من المتأخّرات ومن عبء العمل |
| **متى** أُنجِزت؟ | عند **أول** دخول إلى `DONE` فقط |

لذلك يوجد **تعبير واحد مشترك** لا اثنان:

```ts
// packages/types/src/domain.ts
isCompleted(category)          // DONE أو CLOSED — أي: "ليست مفتوحة"
COMPLETED_CATEGORIES           // نفس المجموعة، بصيغة تقبلها مرشِّحات Prisma
```

وتستعمله `overdue()` و`workload()` في `apps/api/src/reports/reports.service.ts`.
أمّا `completed()` فتبقى على `DONE` **وحدها** عن قصد: النقل إلى «انتهى» خطوة
لاحقة على مهمة أُنجِزت أصلًا، فلو عُدّ إنجازًا لظهرت المهمة **مرّتين** في تقرير
المُنجَز خلال نفس الأسبوع. (انظر [`11-reports.md`](./11-reports.md).)

## ماذا حدث لـ «بانتظار تقييم» (`REVIEW`)؟

كانت ضمن القالب قبل إضافة `CLOSED`، ولم تعد تُبذَر للوحات الجديدة. لكنها **بقيت
قيمة صالحة** في `ListStatusCategory`، لأن اللوحات المُنشأة قبل التغيير ما زالت
تملك قائمة تحملها — وقد تحتوي بطاقات. حذف القيمة كان سيُفشل المِهجرة، وحذف
القائمة كان سيضيّع عملًا.

## المِهجرة: ماذا حدث للوحات القائمة

مِهجرتان منفصلتان (`20260824170000_add_closed_status_category` ثم
`20260824170100_backfill_closed_status_lists`). السبب في الفصل أن Postgres لا
يسمح **باستعمال** قيمة enum جديدة داخل نفس المعاملة التي أضافتها، وPrisma يشغّل
كل ملف مِهجرة في معاملة واحدة.

ما تفعله مِهجرة البيانات على كل لوحة تملك قائمة واحدة على الأقل بفئة غير `null`:

1. **تُضيف** قائمة «انتهى» بفئة `CLOSED` إن لم تكن موجودة (عملية جامدة
   Idempotent — إعادة تشغيلها لا تُضيف نسخة ثانية).
2. **تُعيد الترتيب** إلى الترتيب المعتمد:
   `NEW → READY → IN_PROGRESS → REVIEW → DONE → CLOSED`، ثم القوائم اليدوية
   (`statusCategory = null`) في آخر اللوحة محتفظةً بترتيبها النسبي — فهي أعمدة
   أنشأها المستخدم ولا شأن للقالب بمواضعها.

**اللوحات اليدوية بالكامل** (كل قوائمها بلا فئة) لا تُمَسّ إطلاقًا.

مفاتيح المواضع الجديدة (`a0`, `a1`, ...) هي نفس المتتالية التي يولّدها
`generateKeyBetween(prev, null)` من `@app/ordering`، فتبقى صالحة كمدخل لأي نقل
لاحق (انظر [`06-ordering.md`](./06-ordering.md)). وتحتوي المِهجرة على حارس
يُفشلها بصوت عالٍ لو وُجدت لوحة بأكثر من 62 قائمة، بدل أن تكتب مواضع مكرّرة
بصمت.

## لماذا حقل `statusCategory` وليس الاسم فقط؟

اسم القائمة **قابل للتغيير ومترجَم**؛ لو اعتمدت التقارير على مطابقة الاسم العربي
"تم التنفيذ" لانكسرت عند أي إعادة تسمية. لذلك تحمل كل قائمة مُنشأة من قالب حقلًا
اختياريًا `statusCategory` (enum) يُبقي **المعنى** ثابتًا بمعزل عن الاسم — وأهمّه
الحالتان النهائيتان `DONE` و`CLOSED` اللتان يعتمدهما قسم التقارير (انظر
[`11-reports.md`](./11-reports.md)).

- القوائم المُنشأة يدويًا (خارج القالب) تحمل `statusCategory = null`، وتُعامَل في
  التقارير على أنها **ليست منتهية** (not-done).
- الحقل حاليًا **إعلامي فقط** لأغراض التقارير؛ لا يفرض قيودًا على النقل بين القوائم،
  ولا يمنع تعديل اسم القائمة.

## متى يُطبَّق القالب؟

القرار المُثبَّت: **عند إنشاء اللوحة فقط**. يقبل طلب إنشاء اللوحة حقلًا اختياريًا:

```
POST /boards   { name, description?, template?: "EMPTY" | "TASK_WORKFLOW" }
```

- `EMPTY` (الافتراضي على مستوى الـ API عند حذف الحقل) — يحافظ على السلوك التاريخي:
  لوحة بلا قوائم.
- `TASK_WORKFLOW` — تُنشأ اللوحة **وقوائمها الخمس** داخل نفس عملية الإنشاء.

ملاحظة عن الواجهة: نموذج إنشاء اللوحة في `apps/web` يختار مسبقًا `TASK_WORKFLOW`
(القيمة الافتراضية في القائمة المنسدلة) لتبدأ اللوحات الجديدة بقوائم الحالات الخمس
بترتيبها الصحيح، مع إمكانية اختيار "لوحة فارغة" يدويًا. الافتراض على مستوى الـ API عند
حذف الحقل يبقى `EMPTY` دون تغيير.

مواضع القوائم (`position`) تُولَّد دفعةً واحدة عبر
`generateNKeysBetween(null, null, 5)` من `@app/ordering`، فتأتي مفاتيح مرتّبة
وفريدة بترتيب الحالات (انظر [`06-ordering.md`](./06-ordering.md)). لا يوجد بذر
لأي بطاقات — القوائم فقط.

## التوسّع لاحقًا

القالب حاليًا **واحد مبني في الكود** (`TASK_WORKFLOW_TEMPLATE`). إضافة قوالب أخرى
تعني توسيع enum `BoardTemplate` في `packages/types` وإضافة مصفوفة قوائم جديدة في
`board-templates.ts`. القوالب القابلة لتخصيص المستخدم مؤجّلة.
