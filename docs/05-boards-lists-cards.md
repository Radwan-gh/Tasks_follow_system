# 5. منطق اللوحات والقوائم والبطاقات

المصدر: `apps/api/src/boards/boards.service.ts`،
`apps/api/src/lists/lists.service.ts`، `apps/api/src/cards/cards.service.ts`،
وأشكال الطلبات في `packages/types/src/requests.ts`.

## واجهة الـ API (نظرة سريعة)

كل المسارات تتطلّب مصادقة (Bearer JWT) ما عدا `/auth/*`.

- **اللوحات:** `GET/POST /boards`، `GET /boards/archived`، `GET/PATCH/DELETE /boards/:id`،
  `GET /boards/:id/summary`، `PUT/POST /boards/:id/members`،
  `DELETE /boards/:id/members/:userId`، `PATCH /boards/:id/members/:userId/role`،
  `GET /boards/:id/member-candidates`
- **القوائم:** `POST /boards/:boardId/lists`، `PATCH/DELETE /lists/:id`
- **البطاقات:** `POST /lists/:listId/cards`، `GET/PATCH/DELETE /cards/:id`،
  `GET /cards/:id/history`، `PATCH /cards/:id/access`، `PATCH /cards/:id/assignees`
- **المهام الفرعية والتقارير:** لها ملفّاها المخصّصان
  ([`10-subtasks-and-assignment.md`](./10-subtasks-and-assignment.md) و
  [`11-reports.md`](./11-reports.md)).

## اللوحات (Boards)

### الإنشاء
- ينشئ اللوحة ويُسجّل منشئها كعضو **OWNER** في نفس العملية.
- يبذر خمس قوائم حالات ضمن نفس العملية افتراضيًا. الحقل الاختياري `template`
  يبقى في الـ API: `TASK_WORKFLOW` (الافتراضي عند حذفه) أو `EMPTY` (لوحة بلا
  قوائم). الواجهتان (الويب والجوال) **لا ترسلانه ولا تعرضان أي اختيار قالب**.
  التفاصيل في [`09-list-status-templates.md`](./09-list-status-templates.md).

### القائمة (List for user)
- تُرجَع فقط اللوحات التي المستخدم **عضو** فيها و**غير مؤرشفة**، مرتّبة بالأحدث تحديثًا.

### التفاصيل (Detail)
- يتطلّب عضوية (MEMBER على الأقل).
- يُرجِع اللوحة مع أعضائها وقوائمها **غير المؤرشفة** مرتّبة بالموضع، وداخل كل قائمة
  بطاقاتها **غير المؤرشفة** مرتّبة بالموضع.
- كل بطاقة هنا من نوع `BoardCard` (`packages/types`) لا `Card`: البطاقة نفسها مع
  ثلاثة أعداد لوجهها في اللوحة — `subtaskTotal`، `subtaskDone`، `attachmentCount`.
  تُحسب في نفس الاستعلام (`subtasks: { select: { isDone } }` و`_count.attachments`)
  فلا طلب لكل بطاقة. **هذا المسار وحده** يحملها؛ بقية مسارات البطاقة
  (`GET/PATCH /cards/:id`، الإنشاء…) تُرجِع `Card` بلا أعداد.

### التعديل والحذف
- تعديل الاسم/الوصف: MEMBER. أرشفة اللوحة (أو استعادتها بـ`isArchived: false`): OWNER.
  الحذف: OWNER، **وللّوحات المؤرشفة فقط** (انظر «الحذف النهائي» أدناه و
  [`04-authorization.md`](./04-authorization.md)).

### الأرشفة — للقراءة فقط (`design-prompt-group-3.md` §3b-3)
- `PATCH /boards/:id { isArchived: true }` (OWNER فقط) يجعل اللوحة **للقراءة فقط**:
  `BoardsService.assertBoardMutable(boardId)` تُستدعى في بداية كل عملية تعديل عبر
  `ListsService`/`CardsService`/`SubtasksService`/`CommentsService.create`/
  `AttachmentsService.create` وتُلقي 403 إن كانت اللوحة مؤرشفة — بمعزل تامّ عن
  `assertMembership` حتى تبقى **مسارات القراءة** (`getDetail` وغيرها) تعمل بلا قيد على
  لوحة مؤرشفة. لا تُطبَّق على الحذف (`remove`) في أيّ من هذه الخدمات — يبقى ممكنًا
  تنظيف محتوى قديم حتى بعد الأرشفة.
- `GET /boards/archived` (`BoardsService.listArchivedForUser`) تُرجع لوحات المستخدم
  المؤرشفة فقط — نظير `GET /boards` تمامًا لكن بعكس شرط `isArchived`.
- الاستعادة (`isArchived: false`) متاحة للمالك فقط من نفس مسار `PATCH /boards/:id`.
- `ReportsService.overdue()`/`workload()` (انظر [`11-reports.md`](./11-reports.md))
  تستثنيان بطاقات أي لوحة مؤرشفة.

### الحذف النهائي — بعد الأرشفة فقط
- `DELETE /boards/:id` (`BoardsService.remove`، عبر `api.boards.remove` في
  `packages/api-client`) يتطلّب **OWNER**، ويرفض بـ **409** (`ConflictException`) أيّ
  لوحة غير مؤرشفة. الأرشفة إذن هي الخطوة الأولى القابلة للتراجع دائمًا، ولا يمكن مسح
  لوحة نشطة بضغطة واحدة.
- القوائم والبطاقات وسجلّ النشاط والتعليقات والمرفقات والأعضاء والقوالب تُحذف تلقائيًا
  بـ`onDelete: Cascade` في المخطّط. أما الإشعارات (`Notification`) فتحمل `boardId`
  نصيًّا بلا مفتاح أجنبي، لذا تُحذف صراحةً **في نفس المعاملة** مع اللوحة حتى لا يبقى
  إشعار يفتح لوحة غير موجودة.
- ملفات المرفقات نفسها (القرص أو الـbucket) تُحذف بعد نجاح المعاملة عبر
  `AttachmentStorageService.remove` — بأفضل جهد، فغياب ملف ليس خطأً. لهذا صار
  `AttachmentStorageService` مُقدَّمًا ومُصدَّرًا من `BoardsModule` (ويصل إلى
  `CardsModule` عبر استيرادها له).
- الواجهات: زر «حذف اللوحة» يظهر للمالك في إعدادات اللوحة **فقط حين تكون مؤرشفة**
  (مكان زر «أرشفة اللوحة»). على الويب (`BoardSettingsModal`) تأكيد بخطوتين ثم الانتقال
  إلى `/boards/archived`؛ وعلى الجوال `ConfirmSheet` بصيغة `typeToConfirm` (كتابة اسم
  اللوحة) ثم الرجوع إلى `/archived-boards`.

### إدارة الأعضاء
- **الاستبدال الكامل (OWNER) — `PUT /boards/:id/members`:** المصدر
  `BoardsService.setMembers`، والطلب `SetBoardMembersRequestSchema = { userIds }` — نفس
  شكل `UpdateAssigneesRequestSchema` تمامًا، لأن الواجهتين تُديران العضوية بنفس منتقي
  الأشخاص ذاتي الحفظ المستخدَم لإسناد المهام (انظر «في الواجهات» أدناه). يُحسَب الفرق مع
  الأعضاء الحاليين ويُطبَّق في **معاملة واحدة**:
  - **الجدد** يُضافون بدور **MEMBER** دائمًا (تبديله إلى مشاهد لاحقًا بمسار الدور). يُرفض
    الطلب كلّه إن لم يوجد أحدهم ("No such user") أو كان **معطَّلًا** — نفس قاعدة الإضافة
    أدناه: المنع يخصّ العضويات الجديدة فقط، ومن عُطِّل بعد انضمامه يبقى.
  - **من بقي** يحتفظ بدوره كما هو.
  - **المحذوفون** تُحذف عضويتهم مع صفوف وصولهم الخاصّ لبطاقات هذه اللوحة
    (`CardMember`) — كما في الإزالة الفردية.
  - **المالك يبقى دائمًا** سواء أُدرج في `userIds` أم لا، فلا يمكن لهذا المسار إزالته.
  - التكرار يُدمَج، والاستجابة قائمة الأعضاء الناتجة (`BoardMember[]`).
- **الإضافة (OWNER):** يُرسَل الطلب بـ **`userId`** (لا ببريد ولا باسم مستخدم) —
  `AddBoardMemberRequestSchema = { userId, role? }`. يُرفض إن لم يوجد المستخدم، أو إن
  كان عضوًا بالفعل، أو إن كان **حسابه معطَّلًا** (`isActive = false`) →
  "Cannot add a deactivated user to a board". يُضاف بدور **MEMBER** افتراضيًا، أو
  **VIEWER** إن أُرسل `role` صراحةً في الطلب.
  > الحساب المعطَّل لا يسجّل الدخول ولا يُسنَد إليه عمل، فلا ينضمّ للوحة أصلًا. أمّا
  > **العضويات القائمة فلا تُمسّ** عند التعطيل (انظر [`07-admin.md`](./07-admin.md))
  > — المنع يخصّ العضويات الجديدة فقط.
  >
  > المعرّف يأتي دائمًا من صفّ في نتيجة `member-candidates` أدناه، فلا يحوّل الخادم
  > نصًّا كتبه إنسان إلى حساب إطلاقًا. هذا ما أزال مسار البحث بالبريد نهائيًا، وهو
  > ضروري بعدما صار البريد اختياريًا (حساب بلا بريد كان سيتعذّر إضافته).
- **البحث عن مرشّحين للإضافة (OWNER) — `GET /boards/:id/member-candidates`:** المصدر
  `BoardsService.listMemberCandidates`. يستقبل `search` اختياريًا (مطابقة **جزئية غير
  حسّاسة لحالة الأحرف** على **اسم المستخدم** أو الاسم المعروض) و`limit` (افتراضيًا 20،
  بحدّ أقصى 50)، ويُرجِع `{ users, hasMore }` (`BoardMemberCandidateList` في
  `packages/types`).
  - **نفس صلاحية الإضافة تمامًا** (`assertMembership(..., "OWNER")`) — فلا يوسّع هذا
    المسار من يرى دليل المستخدمين. وهو الآن **الطريق الوحيد** للعثور على من يُضاف،
    إذ لم تعد `addMember` تقبل نصًّا يُبحَث به.
  - **يستثني أعضاء اللوحة الحاليين** (`boardMemberships: { none: { boardId } }`) فكل
    صفّ مُرجَع قابل للإضافة فعلًا.
  - **`search` فارغ طلبٌ صالح ومقصود:** فتح المنتقي يعرض أوائل المرشّحين مباشرةً، فلا
    يواجه المستخدم صندوقًا فارغًا لا يعرف بماذا يبدأ.
  - **يستثني المستخدمين المعطَّلين** (`isActive: true`) مطابقةً لما ترفضه `addMember` —
    عرض صفّ معطَّل لا يثمر إلا طلبًا فاشلًا. لذلك صار الترتيب بالاسم المعروض وحده
    (لم تعد هناك حاجة لتقديم المفعّلين).
  - يُجلَب صفّ إضافي واحد (`take: limit + 1`) لحساب `hasMore` دون استعلام عدّ ثانٍ.
- **الإزالة (OWNER):** يُرفض إن لم توجد العضوية، و**يُمنع إزالة عضو دوره OWNER**.
- **في الواجهات: نفس منتقي إسناد المهام حرفيًا.** الويب `BoardMembersModal.tsx`
  (`UserTypeahead`) والجوال شاشة إعدادات اللوحة (`PeopleField`): الأعضاء رقائق، والكتابة
  تُظهر **أفضل 3 مطابقات** (`topMatches`: البادئة أولًا ثم أبجديًا)، وEnter أو النقر يضيف،
  و✕ الرقاقة يزيل — وكل إضافة/إزالة تُحفَظ **فورًا** عبر `useAutoSavedIds` →
  `PUT /boards/:id/members`، بلا زرّ حفظ ولا نافذة تأكيد، مثل المسؤولين عن المهمة تمامًا.
  الفرق الوحيد مصدر الاقتراحات: ما يُكتب يُرسَل (بتأخير 150ms) إلى `member-candidates`
  بـ `limit=50`، ثم يُرتَّب محليًا بنفس `topMatches`؛ ولا يُطلب شيء قبل الكتابة. رقاقة
  المالك بلا ✕ وعليها «مالك»، ولكل رقاقة أخرى زرّ دور صغير («عضو ▾»/«مشاهد ▾») يبدّل الدور
  بمسار الدور أدناه. لغير المالك (الجوال فقط، فالويب لا يفتح النافذة له) تُعرض الرقائق
  للقراءة. تفاصيل قاعدة «كل مكان يُختار فيه مستخدم قابل للبحث»
  في [`12-mobile-app.md`](./12-mobile-app.md).
- **تبديل الدور (OWNER) — `PATCH /boards/:id/members/:userId/role`:** يبدّل عضوًا قائمًا
  بين `MEMBER` و`VIEWER` فقط (لا يصل لـ`OWNER` أبدًا عبر هذا المسار)؛ تفاصيل دور
  «مشاهد» الكاملة في [`04-authorization.md`](./04-authorization.md).

### ملخّص اللوحة للمالك — `GET /boards/:id/summary`
`BoardsService.summary` (OWNER فقط عبر `assertMembership(..., "OWNER")`) يحسب أربعة
أرقام دفعة واحدة، بديلًا عن قسم `/reports/*` المحكوم بصلاحية ADMIN
(`design-prompt-group-3.md` §3b-5):
- **منجز آخر 7 أيام:** عدد البطاقات المميّزة (dedup) التي دخلت قائمة `DONE`/`CLOSED`
  خلال آخر أسبوع، بنفس منطق إزالة التكرار في `ReportsService.completed` (بطاقة نُقلت
  أكثر من مرة تُحسب مرة واحدة).
- **المتأخّرة:** نفس شرط `ReportsService.overdue` لكن مقصورًا على هذه اللوحة.
- **توزيع الأعباء:** أعلى 3 أشخاص بعدد البطاقات المفتوحة المُسنَدة إليهم
  (`workload`)، وعدد الباقين في `workloadRestCount` — لا قائمة كاملة.
- **تكلفة الشهر:** مجموع `Card.costAmount` للبطاقات التي أُنشئت هذا الشهر التقويمي؛
  `null` (وليس `"0"`) إن لم توجد أي بطاقة بتكلفة بعد، حتى لا يُعرض رقم صفري مضلِّل.

## القوائم (Lists)

### الإنشاء
- يتطلّب عضوية. يُحسب موضع القائمة الجديدة بحيث تُضاف **في نهاية** اللوحة، عبر قراءة
  آخر قائمة غير مؤرشفة وتوليد مفتاح بعدها (`nextListPosition`).

### التعديل وإعادة الترتيب
- يمكن تعديل الاسم أو حالة الأرشفة.
- إعادة الترتيب تتم عبر حقل `move: { beforeId, afterId }` (انظر أدناه "شكل طلب النقل").
- يُتحقّق أن معرّفات الجيران المُرسلة تنتمي فعلًا **لنفس اللوحة** وأنها ليست القائمة
  نفسها المُحرَّكة، وإلا يُرفض بـ "Invalid move target".

### الحذف
- يتطلّب عضوية؛ يحذف القائمة وبطاقاتها (حذف متسلسل).

## البطاقات (Cards)

### الإنشاء
- تحت قائمة محدّدة؛ يتطلّب عضوية في لوحة القائمة.
- تُضاف **في نهاية** القائمة (`nextCardPosition`)، ويُسجَّل منشئها في `createdById`،
  ويُنسَخ `boardId` من القائمة.

### التعديل والنقل — أهم منطق في هذا الملف
دالة `CardsService.update` تغطّي عدّة حالات في آنٍ واحد:

1. **تعديل الحقول فقط** (عنوان/وصف/تاريخ استحقاق/أرشفة) دون نقل.
2. **النقل داخل نفس القائمة** عبر `move: { beforeId, afterId }`.
3. **النقل إلى قائمة أخرى** عبر `targetListId`:
   - يُتحقّق أن القائمة الهدف **تنتمي لنفس اللوحة**؛ يُرفض النقل بين لوحتين مختلفتين
     ("Cannot move a card to a list on a different board").
   - **النقل إلى قائمة فئتها `CLOSED` («انتهى»)** مقصور على **مالك اللوحة** أو
     **المسؤولين عن البطاقة نفسها** (`card.assignees`) — تعديل لقرار سابق كان متاحًا
     لأي عضو، انظر `design-prompt-group-3.md` §3b-4. أي عضو آخر يحاول هذا النقل تحديدًا
     يُرفض بـ 403؛ النقل لأي قائمة أخرى يبقى متاحًا لكل الأعضاء كما كان.
   - إن أُرسلت معرّفات الجيران يُتحقّق أنها تنتمي **للقائمة الهدف** وأنها ليست البطاقة
     نفسها.
   - إن نُقلت لقائمة أخرى **دون تحديد جيران**، تُوضع **في نهاية** القائمة الهدف.
4. **الأولوية** (`priority: LOW | NORMAL | URGENT`، الافتراضي `NORMAL`) تُكتب فعليًا في
   كلٍّ من الإنشاء والتعديل. «عاجل» فقط يظهر كمؤشر على وجه
   البطاقة (شريط حافة) وفي ترتيب عرض الجوال — العمود يعرض العاجل أولًا ثم الباقي بترتيبه
   اليدوي، و«مهامي» يعرض المتأخّر ثم العاجل؛ الترتيب الفعلي (`position`) لا يتغيّر، هذا
   ترتيب عرض فقط يحسبه العميل (`sortByPriority` في `apps/mobile`). لا يُسجَّل تغيير
   الأولوية في سجل البطاقة (`CardActivity`) — بلا نوع نشاط مخصّص له.
5. **التكلفة** (`costAmount`/`costNote`، §3c-1) تُكتب فعليًا الآن في الإنشاء والتعديل
   (كانت في المخطّط والاستجابة فقط منذ المرحلة 1، غير موصولة). تغييرها يُسجِّل نشاط
   `COST_UPDATED` في سجل البطاقة (`fromValue`/`toValue` = المبلغ القديم/الجديد كسلسلة
   نصية، أو `null`) — فقط حين تتغيّر القيمة فعليًا، بنفس نمط باقي حقول `diffActivities`.
   لا تُنسَخ التكلفة عند توليد النسخة المتكرّرة التالية (`spawnNextRecurrence`) — نطاق
   متعمَّد، انظر [`14-notifications-comments-attachments.md`](./14-notifications-comments-attachments.md#recurring-task-generation).
6. **وقت التسليم الاختياري** (`dueDateHasTime`، §3c-5): `dueDate` نفسه دائمًا طابع زمني
   كامل في قاعدة البيانات؛ هذا الحقل المنطقي (افتراضه `false`) هو ما يُخبر العميل هل
   يعرض/يستخدم جزء الوقت أم يتجاهله ويعامل القيمة كتاريخ فقط. يُكتب مع `dueDate` في نفس
   الطلب.

كل حساب للموضع يجري **داخل معاملة Prisma واحدة**، بإعادة قراءة مواضع الجيران طازجةً ثم
حساب المفتاح الجديد على الخادم. النتيجة: **موضع قديم أرسله العميل لا يمكن أبدًا أن يُفسد
الترتيب** (تفاصيل الخوارزمية في [`06-ordering.md`](./06-ordering.md)).

### الحذف
- يتطلّب عضوية في لوحة البطاقة.

## قوالب المهام (Task Templates) — §3c-3

المصدر: `apps/api/src/templates/*` (`TemplatesService`/`TemplatesController`).

> **أُزيلت من الواجهات:** لا تعرض أي من الواجهتين (الويب والجوال) قوالب المهام بعد
> الآن — لا منتقي في «إضافة مهمة»، ولا «حفظ كقالب»، ولا قسم «قوالب المهام» في
> إعدادات اللوحة. المسارات أدناه وطرق `api.templates`/`api.cards.saveAsTemplate` في
> `packages/api-client` باقية في الخادم دون مستهلك في الواجهة.

```
GET/POST    /boards/:boardId/templates
PATCH/DELETE /boards/:boardId/templates/:templateId
POST        /cards/:id/save-as-template
```

- **قراءة القائمة:** أي عضو (حتى VIEWER).
- **الإنشاء/إعادة التسمية/الحذف:** مالك اللوحة فقط (`assertMembership(..., "OWNER")`)
  + `assertBoardMutable` (لا تعديل قوالب على لوحة مؤرشفة).
- **`POST /cards/:id/save-as-template`** (مالك اللوحة فقط): الخادم — لا العميل — يقرأ عنوان البطاقة ووصفها ومهامها الفرعية الحالية
  (بترتيبها) ويُنشئ منها قالبًا؛ الطلب يحمل الاسم فقط. هذا يُبسِّط العميل ويضمن تطابق
  القالب مع حالة البطاقة **لحظة الحفظ**، لا لحظة فتح الشاشة.
- **`Template` مستقل عن `TASK_WORKFLOW_TEMPLATE`** (`board-templates.ts`): الأخير يبذر
  **قوائم اللوحة** عند الإنشاء (انظر [`09-list-status-templates.md`](./09-list-status-templates.md))،
  بينما `Template` يعبّئ **بطاقة جديدة**. تسمية مختلفة عمدًا لتفادي الخلط.

## شكل طلب النقل (Move Request) — قاعدة موحّدة

كل طلبات إعادة الترتيب (للقوائم وللبطاقات) تشير إلى **معرّفات الجيران** لا إلى سلاسل
الموضع الخام:

```
PATCH /lists/:id   { move: { beforeId, afterId } }
PATCH /cards/:id   { targetListId?, move: { beforeId, afterId } }
```

- `beforeId` = العنصر الذي سيقع **قبل** العنصر المُحرَّك (أعلاه/يمينه حسب الاتجاه).
- `afterId` = العنصر الذي سيقع **بعده**.
- أيٌّ منهما قد يكون `null` (يعني الطرف: البداية أو النهاية).

الخادم يُعيد قراءة مواضع هذين الجارين **لحظة التنفيذ داخل المعاملة** ويحسب المفتاح
الجديد بينهما بنفسه؛ لذا يُمنع أن يُرسل العميل سلسلة موضع محسوبة مسبقًا.

## سلوك الواجهة أثناء السحب (dnd-kit)

في `apps/web/src/features/boards/BoardPage.tsx`:
- القوائم داخل `SortableContext` أفقي؛ وبطاقات كل قائمة داخل `SortableContext` رأسي
  متداخل.
- كل عنصر قابل للسحب يحمل وسمًا `data: { type: 'list' | 'card' }` للتمييز بين "إعادة
  ترتيب الأعمدة" و"نقل بطاقة".
- القوائم الفارغة تحتاج منطقة إفلات مخصّصة (`${list.id}::empty`) لأن `SortableContext`
  الفارغ لا يملك عنصرًا يُسجَّل كهدف تحويم.
- مع `closestCorners` يكون هدف الإفلات (`over`) أقرب عنصر قابل للإفلات، وقد يكون بطاقة
  أو منطقة إفلات قائمة فارغة داخل العمود الهدف — وليس القائمة نفسها. لذلك يجب على كلا
  الفرعين (نقل بطاقة وإعادة ترتيب القوائم) في `onDragEnd` أن يُرجعا هدف الإفلات إلى
  معرّف قائمة عبر `resolveTargetListId()` الذي يوفّق أشكال `over` الثلاثة
  (`list` / `list-dropzone` / `card`). فرع إعادة ترتيب القوائم إن قارن `over.id` مباشرةً
  بمعرّفات القوائم فسيحصل على `-1` في الغالب (لأن `over` بطاقة) ويسقط النقل بصمت، فتعود
  المواضع إلى ترتيبها المحفوظ عند إعادة تحميل الصفحة.
- الحالة المحلية تُحدَّث تفاؤليًا (Optimistic) أثناء السحب، ثم تُوفَّق مع الخادم عند
  الإفلات بإرسال معرّفات الجيران المحسوبة من المصفوفة المحلية — بما يطابق واجهة النقل في
  الخادم.

## التحقّق من الطلبات (Validation)

لا يُستخدم `ValidationPipe` الافتراضي في Nest؛ بل تُتحقَّق أجسام الطلبات بنفس مخطّطات
**zod** المُعرَّفة في `packages/types` عبر `ZodValidationPipe` مخصّص يُطبَّق لكل معامل:
`@Body(new ZodValidationPipe(SomeRequestSchema))`. الهدف: تعريف أشكال الطلب/الاستجابة
مرة واحدة يستوردها الطرفان.
